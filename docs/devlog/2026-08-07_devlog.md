**Real bugs fixed:**

- **Level-1 badge never unlocked.** The badge-crossing logic requires
  `before.level < badge.level` — but everyone starts AT level 1, so that
  condition can never be true for the level-1 badge. Screenshot
  confirmed it: badge 1 grayed out, badge 2 lit up. Now unlocked
  unconditionally (idempotent) on `load()`.
- **Ghost-text suggestions never appearing.** Live-tested it: a cold
  `dolphin-phi` load took ~6.2s on this machine (Ollama unloads idle
  models by default, so cold is the normal case, not rare), longer than
  the 6000ms suggestion timeout. Raised the timeout to 12s and added a
  warm-up call fired when Zen mode opens, so the model's usually already
  loaded by the user's first typing pause.
- **AI-assist project notes vanishing.** Sub-tasks/scheduling/tighten-
  description/ask were deliberately ephemeral by an earlier design call
  ("shown once, discarded") - Jeremy's own testing found that surprising
  in practice. New `project_assist_notes` table, real persisted history
  now, same treatment status reports already got.
- **Project Save gave no feedback.** Now closes the card and returns to
  the list.
- **Target month was a 3-4 option hardcoded dropdown**, not a real
  picker. Swapped for a native month/year control. Completion-goal
  calendar/time picker now also shows on project creation, not just
  edit.
- **Todo reminders didn't exist in the UI** despite the store already
  supporting them - added a "Remind me" toggle + time field, a display
  on todos that have one, and a working Snooze button (the store method
  existed, nothing called it anywhere).
- **Library had no visible export.** Journals already auto-export to
  `docs/workjournal/` on generation - true, but invisible. Added a real
  Export button with a "Saved to ..." confirmation.
- **Progress tab:** earned badges now render bigger (56px vs 36px
  locked) with a hover animation; locked stay small and static. Full-
  screen project-detail form was stretching edge-to-edge into unreadably
  wide fields at 2x zoom - capped and centered.

**Not fixed, and why:** the clock-in/out/break voice cues are pre-baked
WAV files generated once via a separate TTS engine (Chatterbox-Turbo,
not Piper) — switching the "default voice" setting to Amy never touched
them, since they're static assets, not live calls. Regenerating them in
a female voice needs either Chatterbox or Piper actually running, and
neither was reachable tonight. Same story for "no autosuggestions

## 23:10 — Grok 4.5 toggle, off by default, and the cancel plumbing it needed

Jeremy dropped this mid-turn while I was mid-build on the next feature:
Settings needs a toggle for Grok 4.5 (his own paid cloud subscription),
off by default. Straightforward on its face, but "off by default"
matters — every AI call site in the app had to actually route through
one place that decides local-vs-cloud, not just the obvious ones.

Landed `resolveModelOverride(grok4Enabled)` in `openclawClient.ts` as
the single source of truth: off resolves to `ollama/hermes3:8b`
explicitly, on resolves to `undefined` (don't override, let OpenClaw's
own default apply — which is Grok already). Threaded that through all
four real call sites: journal generation, project assist (both the
freeform-question path and the report generator), capture routing, and
the check-in conversation flow. The setting itself lives in the same
`app_settings` key-value store as everything else, read reactively in
React components via `useSettingsStore`, read directly via
`repos.settings.get()` in the non-component stores (captureStore,
journalsStore) that fire these calls without a hook.

While I was in `openclaw.rs` anyway, went ahead and built the piece the
next feature (exit confirmation) is going to need: a real way to cancel
an in-flight OpenClaw subprocess call, not just abandon it. Added a
shared `Arc<AtomicBool>` cancel flag as managed Tauri state, checked
inside `run_cli`'s existing poll loop right next to the timeout check —
reused the already-proven kill path instead of building new process
tracking. New `cancel_active_agent_call` command flips the flag; each
call resets it to false at the start so a stale cancel from a previous
run can't leak into the next one.

Eighteen test fixtures broke from the new required `cancelActiveCall`
method on the fake `OpenClawClient` interface — mechanical fix, one
`sed` pass adding the missing mock method everywhere. Full suite still
448/448 after.

Lint clean (pre-existing Fast-Refresh warnings only, untouched by this
change), `cargo build` and `cargo test` clean (9/9), typecheck clean.
Commit `7021ded`, pushed.

## 23:35 — Exit stops being instant

The other half of what Jeremy asked for: clicking exit used to call
`getCurrentWindow().destroy()` directly, no confirmation, no awareness
of anything still running. That's gone now. Both the pocket-mode power
button and the full-screen File → Exit menu item open a real dialog
instead.

Found the actual design spec for this already sitting in
`docs/reference/next-build-wave-plan.md` (section 2.6, Phase 14 in the
sequencing table) — a plan-mode session wrote this up before I got to
it, so I built to that rather than re-deriving the shape from Jeremy's
message alone. Matched it closely: three real choices when AI is
actively writing something, not just yes/no.

**Detecting "something's in flight"** needed one new piece:
`useAiInFlight()`, a hook that aggregates three independent signals —
a `pending` journal, a `pending` project report, or the capture-agent
mid-classification (`captureStore.phase === "thinking"`) — into one
`{ active, description, discard }` shape. Deliberately left the
forgot-to-clock-out check-in conversation out of this aggregate: it
keeps its own local component state rather than living in a store, and
it already blocks the rest of the UI on its own while open, so there
was nothing meaningful to add by wiring it in too.

**The three real paths:**
- *Wait, then exit* — the dialog just sits in a "waiting" phase; since
  `useAiInFlight` is a live store subscription, the moment the pending
  row resolves on its own the dialog notices and finishes the exit
  automatically. No polling loop, just React doing its normal thing.
- *Exit now anyway* — calls the cancel flag from earlier tonight, then
  a real delete. Added `delete()` to both the journals and
  project-reports repositories for this — previously journals could
  only ever move to `ok`/`failed`, never actually removed. "Removes the
  draft note or journal," per Jeremy's own words, not "leaves it as a
  failed row for the stale-pending sweep to find later."
- *Close to tray instead* — same as a normal window close, offered
  explicitly here too instead of only being reachable by not clicking
  exit at all.

**The goodbye cue holds the window open.** `useSelfVoicing` only had
fire-and-forget `speak()` before tonight — fine for narrating the UI,
not fine for "don't close until the line finishes." Added
`speakAndWait()`, which reuses the exact same one-at-a-time queue but
resolves its returned promise only when that specific utterance's audio
actually ends (or immediately if voicing's off, text's empty, or the
voice call fails — matches `speak()`'s existing fail-soft behavior).
Both real exit paths call this with "Goodbye." before actually
destroying the window.

**Left alone on purpose:** Ctrl+Shift+Q still bypasses all of this —
straight to `app.exit(0)` in the Rust global-shortcut handler, works
even from the tray. Jeremy's wording was about clicking the exit
control specifically, and the shortcut's whole reason for existing is
being a true last-resort. Did clean up the File menu's Exit item, which
used to advertise "Ctrl+Shift+Q" right next to it — that's actively
wrong now since the shortcut and the menu click no longer do the same
thing, so the label had to go. Worth Jeremy weighing in on whether the
shortcut itself should eventually route through the same dialog, or
stay a hard bypass — didn't want to make that call silently.

Hit one real lint error along the way:
`react-hooks/set-state-in-effect` flagged calling `setPhase` from
inside the effect that watches for the in-flight state clearing.
Legitimate case (reacting to an external store, not deriving from
render), so it got a scoped, commented disable rather than a
restructure that would've hidden the actual reason.

19 new tests (`useAiInFlight`, `ExitConfirmDialog`, `speakAndWait`,
the two new repository `discardPending*` store actions), full suite
467/467, typecheck/lint/cargo build+test all clean. Commit `73769df`,
pushed.

## 23:45 — Startup system-check screen, closing out the whole message

Last piece from Jeremy's initializing-phase ask. `SystemStartup` now
sits ahead of the whole onboarding chain — Dashboard's render is gated
behind it before the zen-mode/fullscreen/pocket branches even get a
chance to run.

Three checks, each genuinely different in what "handle it" means:
- **OpenClaw** — already had `openclaw_ensure_daemon` (checks, starts,
  waits up to 15s) from earlier work this build wave. Just needed to
  actually call it here.
- **Voice-Agent** (Piper/faster-whisper) — `ensure_voice_agent_running`
  was built and sitting unused since the exit-flow session (its own doc
  comment already called out "Phase 14-ish, per Jeremy's explicit
  request for a loading screen" — a past planning pass had this
  scoped). Fires `start_all.ps1` (idempotent, self-detaching), then the
  screen polls `voiceClient.isTtsAvailable()` every second until it's
  up or a 20s ceiling gives up.
- **Ollama** — the odd one out. Nothing in this app knows how to start
  it; no launch command exists anywhere in the codebase. Added a plain
  `isAvailable()` health check (`GET /api/version`) to `OllamaClient`
  and left it at report-only, rather than inventing a start mechanism
  that doesn't exist.

**Never blocks Jeremy**, which mattered given his own words earlier
tonight about not having patience to wait around: "Continue now" is
clickable from the very first frame regardless of check state, and a
25-second hard timeout moves on by itself even if something hangs in a
way its own per-check logic doesn't catch. Every AI call site already
degrades gracefully when a backend's unreachable — this screen exists
to make "already running" the normal case, not to gate the app behind
a checklist.

Moved the Welcome cue (from earlier tonight) to fire once this screen
clears instead of on raw settings-load — it was racing Piper's own
startup before, meaning "Welcome" could silently fail to play on a
cold launch even though voicing was enabled the whole time.

**Existing Dashboard tests broke in a genuinely useful way**: five
tests were clicking `screen.getByTitle("Expand to full screen")`
synchronously right after render, assuming the real UI was there
immediately. That assumption's gone now that a startup screen renders
first — fixed by awaiting `findByTitle` on the first interaction in
each, `getBy` after. Also had to give `Dashboard.test.tsx`'s shared
render helper real fast-resolving fakes for OpenClaw/Ollama/voice
instead of letting them fall through to real (slow, unreachable)
implementations — every other Dashboard test was silently paying that
cost too, just under the default `waitFor` timeout by luck.

12 new tests (`SystemStartup`'s six scenarios — clean success, one
backend down, Ollama down, the voice poll loop under fake timers, the
manual skip, the hard-timeout safety net — plus `isAvailable` on
`ollamaClient`), full suite 479/479, typecheck/lint clean. Commit
