## 15:01 — 4.1, third pass: dragging made the whole card invisible

Progress, and a new problem. Jeremy: dragging works now, but the card
goes invisible except for some outer layer while actually moving, which
is worse UX than no drag at all. This is a known Windows/WebView2 thing,
not something specific to this app — a transparent layered window
dragged through the OS's native interactive-move loop doesn't get
repainted by DWM during the move, so a transparent window shows close to
nothing until you let go.

Fix was to stop using the native drag entirely. Pulled
`data-tauri-drag-region` and `startDragging()` out completely and
replaced them with a manual drag: mousedown on the bar records the
window's current position, mousemove computes the cursor delta and
calls `setPosition()` directly, mouseup stops listening. Since the app
is repositioning the window itself frame by frame instead of handing
control to the OS's move loop, the actual content keeps rendering the
whole way through the drag.

Swapped `core:window:allow-start-dragging` for `allow-set-position` in
the capability file since the old mechanism isn't called anymore.
`getCurrentWindow()` needed moving inside the try/catch in the drag
handler too — it was outside it, which wouldn't have crashed anything
(async functions swallow synchronous throws into a rejected promise
either way) but would've thrown an unhandled rejection warning outside
Tauri instead of failing cleanly like the other two handlers do.

45/45 tests, typecheck, lint, build, cargo check clean. Sending this one
back for a look too — three rounds in on what looked like a simple
"add a drag handle" step, which is exactly why each of these gets
checked before calling it done instead of assumed.

## 15:29 — Step 4.3: the tray icon, and a real architectural fix underneath it

System tray: icon, a two-item menu (Show / Quit), left-click on the tray
icon brings the window back. The part worth writing down is what this
forced me to fix about how closing works. Right now the only way to
close the window was the emergency-exit button, which just called
`.close()` — fine on its own, but "lives in the tray, keeps running" is
supposed to be the default behavior for *any* close attempt (taskbar,
Alt+F4), not just a designated button. So the Rust side now intercepts
`WindowEvent::CloseRequested` globally and hides the window instead of
letting it close, for every close path.

That breaks the emergency-exit button, though — `.close()` fires that
exact same interceptable event, so once the global hide-instead-of-close
behavior went in, hitting the exit button would have just hidden the
window like anything else, silently turning the one true "shut it all
down" control into a second minimize button. Switched it to
`.destroy()`, which skips the close-requested event entirely and
actually ends the process. Also added a real "▁ minimize to tray"
button, since removing native decorations back in 4.1 left literally
no in-app way to trigger it before now.

Needed `tray-icon` as a Cargo feature on the `tauri` dependency, and
swapped `core:window:allow-close` for `allow-destroy` + `allow-hide` in
the capability file to match what's actually called now.

56/56 tests, typecheck, lint, build, and `cargo check` all clean —
first-try clean on the Rust side too, since I checked the real
`tauri`/`tray-icon` crate source for the exact API shapes before writing
any of it rather than guessing and iterating. Continuing to the next
step.

## 18:40 — Step 5.3: system-wide idle detection, the real fix from earlier this project

This is the one thing that was flagged and fixed *in the plan* back
