## 12:13 — Data layer, step 2.1: schema, repositories, and a bug the first test run missed

First real code since the rebuild started — SQLite schema for all eight
tables (projects, tasks, task_sessions, session_events, notes, todos,
journals, resource_events), a `SqlExecutor` interface so the repository
code never touches a driver directly, and a typed repository per table.
Tests run against Node's built-in `node:sqlite`, no Tauri runtime needed
for this part.

First full run said 26/26 passing. Reran it verbose right after, same
code, and one test failed: `resourceEventsRepository > lists events
newest first`. Turns out two log calls back to back in the test landed
in the same millisecond, and `ORDER BY occurred_at DESC` has no
tiebreaker for that, so SQLite's own internal order won, not insertion
order. Would've shipped as a real bug — any two auto-resolve actions
close enough together in production hit the same thing. Added `rowid` as
a secondary sort key everywhere a timestamp column gets ordered, not just
the one that failed.

While in there, caught a second one before it became a test failure:
`projects.list()` was sorting by `priority` as plain text — alphabetical
order puts high, low, medium, not the high-medium-low urgency order the
Kanban timeline actually needs. Fixed with an explicit CASE ranking.
Small thing, would've been an annoying one to track down later from a
board that just looked randomly ordered.

## 14:53 — 4.1 follow-up: transparency passed, drag and close silently didn't

Jeremy looked at it for real: transparency itself is right, but he
couldn't drag the window by the bar, and the only way to close it was
right-clicking the taskbar icon. Dug into why and it's a real Tauri v2
thing, not a typo — window action commands are locked behind explicit
permissions separate from query commands. `core:default` pulls in
`core:window:default`, and that set is all read-only (`is-always-on-top`,
`is-focused`, that kind of thing) — `start_dragging` and
`set_always_on_top` aren't in there at all. So my `setAlwaysOnTop()` call
from the pin button was almost certainly failing the same silent way the
drag region was, just nobody had clicked the pin specifically to notice.

Added `core:window:allow-start-dragging` and
`core:window:allow-set-always-on-top` to the capability file. Also added
a real ⏻ exit button while I was in there — leaving Jeremy with no way to
close the app except the taskbar for the rest of this phase would've
blocked his own testing, and File > Exit is designed scope for later
anyway. Wired to `getCurrentWindow().close()`, `core:window:allow-close`
added alongside the other two.

## 15:01 — 4.1, third pass: dragging made the whole card invisible

Progress, and a new problem. Jeremy: dragging works now, but the card
goes invisible except for some outer layer while actually moving, which
is worse UX than no drag at all. This is a known Windows/WebView2 thing,
not something specific to this app — a transparent layered window
dragged through the OS's native interactive-move loop doesn't get
repainted by DWM during the move, so a transparent window shows close to
nothing until you let go.

Fix was to stop using the native drag entirely. Pulled
`data-tauri-drag-region` and `startDragging()` out completely and
replaced them with a manual drag: mousedown on the bar records the
window's current position, mousemove computes the cursor delta and
calls `setPosition()` directly, mouseup stops listening. Since the app
is repositioning the window itself frame by frame instead of handing
control to the OS's move loop, the actual content keeps rendering the
whole way through the drag.

Swapped `core:window:allow-start-dragging` for `allow-set-position` in
the capability file since the old mechanism isn't called anymore.
`getCurrentWindow()` needed moving inside the try/catch in the drag
handler too — it was outside it, which wouldn't have crashed anything
(async functions swallow synchronous throws into a rejected promise
either way) but would've thrown an unhandled rejection warning outside
Tauri instead of failing cleanly like the other two handlers do.

45/45 tests, typecheck, lint, build, cargo check clean. Sending this one
back for a look too — three rounds in on what looked like a simple
"add a drag handle" step, which is exactly why each of these gets
checked before calling it done instead of assumed.

## 15:29 — Step 4.3: the tray icon, and a real architectural fix underneath it

System tray: icon, a two-item menu (Show / Quit), left-click on the tray
icon brings the window back. The part worth writing down is what this
forced me to fix about how closing works. Right now the only way to
close the window was the emergency-exit button, which just called
`.close()` — fine on its own, but "lives in the tray, keeps running" is
supposed to be the default behavior for *any* close attempt (taskbar,
Alt+F4), not just a designated button. So the Rust side now intercepts
`WindowEvent::CloseRequested` globally and hides the window instead of
letting it close, for every close path.

That breaks the emergency-exit button, though — `.close()` fires that
exact same interceptable event, so once the global hide-instead-of-close
behavior went in, hitting the exit button would have just hidden the
window like anything else, silently turning the one true "shut it all
down" control into a second minimize button. Switched it to
`.destroy()`, which skips the close-requested event entirely and
actually ends the process. Also added a real "▁ minimize to tray"
button, since removing native decorations back in 4.1 left literally
no in-app way to trigger it before now.

Needed `tray-icon` as a Cargo feature on the `tauri` dependency, and
swapped `core:window:allow-close` for `allow-destroy` + `allow-hide` in
the capability file to match what's actually called now.

56/56 tests, typecheck, lint, build, and `cargo check` all clean —
first-try clean on the Rust side too, since I checked the real
`tauri`/`tray-icon` crate source for the exact API shapes before writing
any of it rather than guessing and iterating. Continuing to the next
step.

## 15:34 — Step 4.4: the global emergency-exit shortcut

Ctrl+Shift+Q, registered as a real OS-level global shortcut via
`tauri-plugin-global-shortcut`, not an in-window keydown listener. That
distinction matters here specifically: emergency exit is supposed to
work even when the window is hidden to the tray (which is the default
state now, after 4.3), and a normal keydown handler only fires while
the window has focus and exists in the DOM. The Rust side registers the
shortcut once at startup and calls `app.exit(0)` on press - same code
path as the tray's Quit item.

Checked the actual `tauri-plugin-global-shortcut`/`global-hotkey` crate
source for the builder API before writing anything (`with_handler` +
`with_shortcut("ctrl+shift+q")?` + `build()`), same as the tray step -
compiled clean on the first try again. No capability-file changes
needed this time, since the shortcut gets registered from the Rust side
at setup time rather than through a JS-invoked command.

56/56 tests (unaffected, this was a Rust-only step), lint, build,
cargo check all clean. Next.

## 16:01 — Phase 4 test pass, round one: the shadow was getting clipped

Jeremy's read after actually testing it, screenshot in hand: tray,
always-on-top, minimize, both quit paths (⏻ and Ctrl+Shift+Q), all
worked. Transparency itself is "90% good," but the shadow around the
card reads as blocky instead of a realistic soft cast.

Did the math on why instead of just tweaking numbers and hoping. The
shadow was `0 20px 50px -24px rgba(0,0,0,0.5)` — working out roughly how
far a CSS box-shadow's blur actually reaches past the shape's edge
(offset + blur, minus what the negative spread already pulled in), the
visible falloff needed about 46px of room below the card and around
26px on the other three sides. The window only had 20px of margin on
every side (380x520 window around a 340x480 card). The shadow's own
soft gradient was getting hard-clipped by the window boundary before it
finished fading — which is exactly what a clipped gradient looks like:
blocky, not soft.

Fixed two things together, since one without the other doesn't work:
replaced the single shadow with a layered one (three stacked
shadows at different blur/offset/opacity, the standard "realistic
elevation" recipe instead of one flat blur), and grew the window's
margin to 70px a side (480x620 total) so even the biggest layer's
~56-60px reach has real headroom. `useWindowControls`'s pocket-mode
resize target had to move in lockstep or exiting full-screen would
snap back to the old, too-small size.

70/70 tests, typecheck, lint, build, cargo check clean. Can't verify the
visual result myself here — sending it back for another look, along
with a restart since Jeremy's still mid test-pass.
