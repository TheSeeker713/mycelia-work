## 12:13 — Data layer, step 2.1: schema, repositories, and a bug the first test run missed

First real code since the rebuild started — SQLite schema for all eight
tables (projects, tasks, task_sessions, session_events, notes, todos,
journals, resource_events), a `SqlExecutor` interface so the repository
code never touches a driver directly, and a typed repository per table.
Tests run against Node's built-in `node:sqlite`, no Tauri runtime needed
for this part.

First full run said 26/26 passing. Reran it verbose right after, same
code, and one test failed: `resourceEventsRepository > lists events
newest first`. Turns out two log calls back to back in the test landed
in the same millisecond, and `ORDER BY occurred_at DESC` has no
tiebreaker for that, so SQLite's own internal order won, not insertion
order. Would've shipped as a real bug — any two auto-resolve actions
close enough together in production hit the same thing. Added `rowid` as
a secondary sort key everywhere a timestamp column gets ordered, not just
the one that failed.

While in there, caught a second one before it became a test failure:
`projects.list()` was sorting by `priority` as plain text — alphabetical
order puts high, low, medium, not the high-medium-low urgency order the
Kanban timeline actually needs. Fixed with an explicit CASE ranking.
Small thing, would've been an annoying one to track down later from a
board that just looked randomly ordered.

Reran the suite five times after both fixes — 27/27 clean every time.
Committing this as its own step.

## 14:53 — 4.1 follow-up: transparency passed, drag and close silently didn't

Jeremy looked at it for real: transparency itself is right, but he
couldn't drag the window by the bar, and the only way to close it was
right-clicking the taskbar icon. Dug into why and it's a real Tauri v2
thing, not a typo — window action commands are locked behind explicit
permissions separate from query commands. `core:default` pulls in
`core:window:default`, and that set is all read-only (`is-always-on-top`,
`is-focused`, that kind of thing) — `start_dragging` and
`set_always_on_top` aren't in there at all. So my `setAlwaysOnTop()` call
from the pin button was almost certainly failing the same silent way the
drag region was, just nobody had clicked the pin specifically to notice.

Added `core:window:allow-start-dragging` and
`core:window:allow-set-always-on-top` to the capability file. Also added
a real ⏻ exit button while I was in there — leaving Jeremy with no way to
close the app except the taskbar for the rest of this phase would've
blocked his own testing, and File > Exit is designed scope for later
anyway. Wired to `getCurrentWindow().close()`, `core:window:allow-close`
added alongside the other two.

43/43 tests, typecheck, lint, build, cargo check clean. Relaunching for
another look — this is the second round of the same thing: don't call it
done until it's actually been dragged and actually been closed, not just
"the permission line got added."

## 15:01 — 4.1, third pass: dragging made the whole card invisible

Progress, and a new problem. Jeremy: dragging works now, but the card
goes invisible except for some outer layer while actually moving, which
is worse UX than no drag at all. This is a known Windows/WebView2 thing,
not something specific to this app — a transparent layered window
dragged through the OS's native interactive-move loop doesn't get
repainted by DWM during the move, so a transparent window shows close to
nothing until you let go.

Fix was to stop using the native drag entirely. Pulled
`data-tauri-drag-region` and `startDragging()` out completely and
replaced them with a manual drag: mousedown on the bar records the
window's current position, mousemove computes the cursor delta and
calls `setPosition()` directly, mouseup stops listening. Since the app
is repositioning the window itself frame by frame instead of handing
control to the OS's move loop, the actual content keeps rendering the
whole way through the drag.

Swapped `core:window:allow-start-dragging` for `allow-set-position` in
the capability file since the old mechanism isn't called anymore.
`getCurrentWindow()` needed moving inside the try/catch in the drag
handler too — it was outside it, which wouldn't have crashed anything
(async functions swallow synchronous throws into a rejected promise
either way) but would've thrown an unhandled rejection warning outside
Tauri instead of failing cleanly like the other two handlers do.

45/45 tests, typecheck, lint, build, cargo check clean. Sending this one
back for a look too — three rounds in on what looked like a simple
"add a drag handle" step, which is exactly why each of these gets
checked before calling it done instead of assumed.
