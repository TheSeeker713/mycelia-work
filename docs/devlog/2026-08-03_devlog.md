## 12:13 — Data layer, step 2.1: schema, repositories, and a bug the first test run missed

First real code since the rebuild started — SQLite schema for all eight
tables (projects, tasks, task_sessions, session_events, notes, todos,
journals, resource_events), a `SqlExecutor` interface so the repository
code never touches a driver directly, and a typed repository per table.
Tests run against Node's built-in `node:sqlite`, no Tauri runtime needed
for this part.

First full run said 26/26 passing. Reran it verbose right after, same
code, and one test failed: `resourceEventsRepository > lists events
newest first`. Turns out two log calls back to back in the test landed
in the same millisecond, and `ORDER BY occurred_at DESC` has no
tiebreaker for that, so SQLite's own internal order won, not insertion
order. Would've shipped as a real bug — any two auto-resolve actions
close enough together in production hit the same thing. Added `rowid` as
a secondary sort key everywhere a timestamp column gets ordered, not just
the one that failed.

While in there, caught a second one before it became a test failure:
`projects.list()` was sorting by `priority` as plain text — alphabetical
order puts high, low, medium, not the high-medium-low urgency order the
Kanban timeline actually needs. Fixed with an explicit CASE ranking.
Small thing, would've been an annoying one to track down later from a
board that just looked randomly ordered.

Reran the suite five times after both fixes — 27/27 clean every time.
Committing this as its own step.

## 12:42 — Phase 3: task management, first real screen, and a spec bug Enter caught

First real UI since the design got approved. Zustand stores (tasks and
projects, factory pattern so tests get their own isolated instance
instead of sharing global state) wired to the actual repositories from
Phase 2, and a pocket-book-shaped dashboard on top: single-field task
capture, click a task to focus the workspace on it, archive. 340×480,
same paper/moss palette from the mockup, not a placeholder skin.

React Testing Library caught something I wouldn't have found by reading
the code: once you open "+ tag / billable" there are two text fields in
the form, and per the actual HTML spec, a form with two or more text
fields and no submit button doesn't submit on Enter anymore — only forms
with exactly one text field get that implicit behavior. First test run
just hung waiting for a task that never appeared. Real users would've
hit the exact same dead end the moment they wanted to tag something.
Fixed by adding a real default submit button, which restores Enter
regardless of how many fields are open.

Projects got its store and basic CRUD wired too, per the plan, but no
dedicated panel yet — that's deliberately Phase 4's job, once the
pull-tab shell exists to hold it.

40/40 tests, typecheck, lint, and build all clean. Ran `npm run tauri
dev` for real — first cold build took about two minutes compiling the
new sql plugin's dependency tree, then the actual window came up and is
running right now. Couldn't drive it myself with the screenshot tool
