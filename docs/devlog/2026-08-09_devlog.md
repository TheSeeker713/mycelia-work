## 20:05 — Process change: phases stop waiting on me

Changed how this whole thing runs. Phases used to auto-chain their
steps but full-stop at the end of each one, waiting for me to say go
and to do a manual pass in a real window. That was fine when a phase
was three small things. It stopped making sense once the queue got

everything, instead of one after every phase. Everything else stayed
exactly as it was, including the full suite before every commit and
never touching git history.

## 20:14 — Found the ghost-text bug. Two of them, actually

Spent last night proving the backend was fine. Ollama up, model
pulled, the exact request succeeding in four seconds, CORS preflight
clean, system nowhere near the watchdog thresholds. All of that was
true and none of it mattered, because neither bug was in the backend.

Zen mode first. The mirror div that holds the ghost text is
`absolute inset-0`, so it paints first. The textarea right after it is
`relative` with `bg-[var(--paper)]` on it. Both positioned, neither
with a z-index, so the textarea wins on DOM order and its opaque
background covers the mirror completely. The suggestion was rendering
correctly the entire time. I just couldn't see it, because there was
an opaque rectangle sitting on top of it. Moved the background up to
the container and made the textarea transparent.

The Journal was a different bug that happened to look identical from
the outside. Its end-of-document check was
`selection.from === doc.content.size`. That comparison can't ever be
true. In ProseMirror the paragraph's closing token occupies the last
position, so the furthest the caret can actually sit is one below
`content.size`. The guard never passed, Muse never scheduled a single
request, nothing ever hit the network at all. Swapped in
`Selection.atEnd(doc).from`, which resolves the real caret position
instead of me doing offset math badly.

What bothers me is that both of these had passing tests over them.
jsdom has no layout engine, so an element buried under an opaque box
still answers `getByText` perfectly happily. The tests were asserting
"this string is in the DOM," which was always true, rather than "a
person can see this," which was never true. Wrote two new tests that
check the things that actually broke: the textarea must be
transparent with the background on its parent, and typing normally
must produce a real `suggestContinuation` call. Both fail against the
old code.

Also had to polyfill `getClientRects` on Text and Range in the shared
test setup. ProseMirror measures the caret whenever the document
changes and jsdom only stubs that on Element, so the moment a test
typed real characters into the Journal it threw. Same class of gap as
the `elementFromPoint` polyfill from a couple of days ago.

563 tests green, typecheck clean.

## 20:24 — Ghost text in every field now, one mechanism instead of three

Pulled the suggestion logic out of zen mode into `useGhostText` and
built `GhostTextField` on top of it, which is just the mirror-div
trick generalized to work for a plain `<input>` as well as a
`<textarea>`. Zen mode now uses the hook instead of its own copy. The
Journal keeps its ProseMirror decoration, because a mirror div can't
work inside a rich-text document. Two mechanisms, both deliberate,
rather than a third one bolted on for form fields.

It's wired into todos, project title, project description, the
new-project title, the compact Notes panel, the clock-out brief field,
and manual report editing.

Added a minimum of twelve characters before anything fires. Zen mode
used to complete on any non-empty text, which was fine when exactly
one editor did it. With every field in the app doing it, completing
"ab" means a model call on the first keystroke everywhere, all day,
for a suggestion that's pure guesswork anyway.

One thing that fell out of this: the clock-out dialog's test broke,
because a bare textarea needed no app context and a GhostTextField
needs settings, the Ollama client, and the watchdog. Wrapped it in a
real StoreProvider rather than stubbing around it. That's a genuine
new dependency and the test should reflect it.

570 tests, typecheck clean.

## 20:32 — One AI call at a time, everywhere

Built the queue. Every AI call in the app now goes through a single
slot in `services/aiQueue.ts`, so nothing fires alongside anything
else. This matters more now than it did last week, because ghost text
just went from two editors to every field in the app. Without a lock,
typing in a todo while a report generates means two models competing
for the same CPU and both being slow.

Rules per category, since they genuinely differ:

- Journal, report, project assist, check-in, capture: they wait. All
  of these are things I actually asked for, so throwing them away
  would be worse than making them take a minute.
- Ghost text: it drops instead of waiting. Checked when its turn comes
  up, not when it was queued, which is the whole point. A completion
  for a sentence I finished typing two minutes ago is worse than no
  completion at all. It reuses the `requestId` staleness counter the
  hook already had rather than me inventing a second way to say the
  same thing.
- Capture takes one slot for both of its layers. Splitting them would
  mean another job could slide in between the safety check and the
  routing call that depends on it.

The ticker shows what's running, what's behind it, and puts a real
Cancel on every waiting entry. Cancelling something queued is instant
and free, which isn't a design goal so much as a consequence: it
hasn't started, so there's nothing to undo. Ghost text stays out of
the ticker entirely. It resolves itself and there's no decision to
hand me.

One thing this shook loose: the ExitConfirmDialog suite started
failing, and the reason was better than the symptom. One of its tests
deliberately never resolves a call, to prove the "quit now anyway"
path kills it. With a module-level queue, that unresolved call sat in
the slot and blocked every test that ran after it. Added a queue reset
to the shared test setup. The singleton is the right design for an
app-wide lock and the wrong default for a test suite, so it needs the
explicit teardown.

## 20:47 — Making it visible which model actually answered

`model_used` has been sitting in the database since Phase 6 and shown
in exactly zero places. That's the whole reason a request could quietly
land on a local model instead of Grok and just feel slow instead of
looking wrong. Fixed that properly.

New `backend_used` column next to it, because "which model" and "which
service" are different questions and I want both. New
`aiBackendRouter.ts` in front of the OpenClaw client: three connect

against the new one and added the case where both backends genuinely
give up, which is the only path that should still fail now.

## 20:56 — Journal writing finally earns something

The Journal shipped four days ago and earns nothing. Every other store
awards XP, that one never got wired in, so writing in it has been
worth exactly zero this whole time. The rule was written down in the
plan doc long before the feature existed: only manually-typed words
count, anything from a suggestion doesn't.

That rule is the whole interesting part. You can't work out afterward
which words came from Muse, because once accepted text is merged into
the document it looks exactly like typing. So the Muse extension
reports each accepted suggestion through an option callback as it
happens, and the editor keeps a running list to subtract at save time.
Write a whole entry by mashing Tab and you get the flat five for
starting an entry and nothing else, which is the right answer.

Paying per 50-word block instead of per word. Per-word made a long
evening of writing worth more than finishing an entire project, which
is obviously wrong.

`sticker_first_journal_entry` has been sitting in the catalog with real
art since Phase 13, marked reserved and unreachable. It unlocks now.

Packaging targets NSIS only now instead of the scaffold's "all", which

code. It needs a signing keypair, and generating a long-lived
credential and deciding where it lives isn't mine to do. And this repo

workflow already reads the signing secrets under the right names, so
the day those exist it starts working without me touching anything.
Wrote the whole thing up in `docs/reference/packaging-and-updates.md`.

Honestly, for a private single-user app on one machine, "reinstall when
there's something worth reinstalling for" is a perfectly good answer
and costs nothing to pick.

## 23:34 — The animate button never worked, and the fix was to stop asking for a key

Found this by re-reading my own report from earlier tonight. The
Reward Gallery's Animate button pulled its API keys out of settings
with a cast, `(settings as unknown as Record<string, string | null>)`,
and that cast was papering over the fact that the three key fields it
was reading had never been added to the settings store. Every lookup
resolved to undefined, every connector reported itself unconfigured,
and the button failed for everyone, every time. The cast is what hid
it. Without it TypeScript would have said so at compile time.

The obvious repair was to add three Settings fields. That's the wrong
repair. Animating a badge you earned shouldn't require signing up
anywhere, and a feature that only works after you've gone and got a
token is a feature that mostly doesn't work.

Public Gradio Spaces solve this properly. Every public Space is an
HTTP API at `/gradio_api/call/{name}`, no token, no login. I didn't
take that on faith. Generated an actual clip from a throwaway 64x64
PNG with no credentials at all, got a real 52KB mp4 back, and
confirmed the Space answers a `tauri://localhost` preflight with
permissive CORS so the webview can call it without a Rust proxy.

The candidate list I started from was wrong, which is why I checked.
LTX-Video, AnimateDiff-Lightning and CogVideoX were the names to try;
what's actually live and busy right now is Wan2.2 image-to-video, on
several forks, RUNNING with multiple replicas. Used HF's own semantic
search endpoint to find them rather than guessing.

Two things cost me real time and are worth writing down.

First, a failed job answers `event: error` with a body of `data: null`.
That's valid JSON. Anything that just parsed the data and moved on
would read a failure as a success. The event name is the only thing
that separates them, so the parser keys on that.

Second, my first attempt failed with exactly that bare error and no
hint why. It wasn't quota. I'd passed `quality: 80` where the Space
wanted 5, `scheduler: "unipc"` where it wanted "UniPCMultistep", and a
string frame multiplier where it wanted the integer 16. Read the
Space's own `app.py` for its real defaults and it worked first try.
Guessing at parameter values gets you a generic error that looks
exactly like being rate limited.

The find I'm happiest about: the two Spaces are forks of the same app
and their signatures have already drifted. The primary takes 17
positional arguments ending safe_mode, lora_groups, video_component.
The mirror takes 16, ends video_component, safe_mode, and has no
lora_groups at all. The API is positional. One shared argument array
would have sent a boolean where a list belongs and failed with that
same useless error. Each Space carries its own builder now, and
there's a test pinning both shapes.

Also fixed a latent crash while I was in there. The old code did
`btoa(String.fromCharCode(...new Uint8Array(buffer)))`, which throws a
call-stack error once the image is big enough, and reward art is big
enough. Chunked it.

fal.ai and Replicate stay, behind optional key fields, worth filling in
only if the free daily limit gets in the way. Anonymous callers share
about two minutes of GPU time a day, which is a couple of clips. That
matches how often anyone wants to animate a badge.

635 tests, up from 622.
