# Devlog — Phase 1: Data Layer

**2026-08-02, 12:40**
**Author: Jeremy Robards, CTO & CAIO, Mycelia Interactive LLC**

Second phase down today, the data layer. This is the part nobody sees but everything else depends on, so I wanted it solid before touching any UI.

Went with SQLite through Tauri's own sql plugin, one migration file that creates all seven tables I planned out: tasks, task sessions, session events, notes, todos, journals, and a resource events table for the watchdog system I'm building later. Every table has exactly what it needs and nothing extra. The task session table has an is_estimated flag baked in from day one, which matters a lot to me because of that ADHD research we pulled up yesterday. When I forget to clock out and the app has to reconstruct what happened, that time gets marked as estimated, not treated the same as time I actually tracked live. I didn't want to bolt that on later, so it's in the schema from the start.

The trickier problem was testing. The real app talks to SQLite through Tauri's plugin, which only works inside the actual running app, not in a normal test runner. I didn't want to test a fake version of my database logic and hope it matches the real thing later. So I had Claude build a small abstraction, one interface both the real plugin and a plain Node SQLite connection can satisfy, and the tests run the literal same repository code against Node's built in SQLite module, using the exact same migration file the real app uses. No duplicated schema, no drift between what's tested and what ships.

Wrote nineteen tests covering the stuff that actually matters. Can you clock into a task twice at once, no. Can you pause a session that's already stopped, no. Can two different tasks run independent timers at the same time without stepping on each other, yes, that one matters a lot since I decided this app needs to support multiple concurrent timers. Notes append in order. Todos can be snoozed and completed. Journals move from pending to ok or pending to failed without losing the row.

Honestly the interesting part of this phase was that the first test run actually failed, three of them. Not because the repository logic was wrong, because I'd written the test data inconsistently. I had one event using a hardcoded past timestamp and the event right before it using the real current time, so of course the real current time came out later than my fake past one and broke the expected order. Small mistake, but I want to write these entries honestly, not just a highlight reel. Fixed the test data, all nineteen passed clean after that, and I read the actual output before believing it, not just the exit code.

Typecheck clean, lint clean, both the frontend build and the Rust build compiling fine with the new sql plugin wired in. Committed, pushed to main.

Task dashboard is next. That's where this will actually start to feel like an app instead of a database with a window attached.

— Jeremy
