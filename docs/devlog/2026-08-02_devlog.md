This whole build, the app, the phases, the tests, all of it, is being

## 12:29 — Phase 0 kickoff

Started building Mycelia Time today. This is the app I've wanted for a
while, something that catches what I'm actually working on and when,
without me having to fight it for an honest log at the end of the day.

Before writing a line of code I had Claude research the psychology
behind why people abandon time trackers and journaling habits instead of
just guessing at features. The Zeigarnik effect kept coming up — an
unfinished or unrecorded task nags at you until it's written down
somewhere you trust. That shaped a lot of my thinking. If capturing a
task is even a little annoying, I won't do it, and the whole system falls
apart. So the plan leans hard on frictionless task capture and clock-in.

We also found something I didn't expect: a study showing people
under-report their actual work hours by close to a full day per week when
asked to recall them after the fact. Not lying, just how memory for time
works, especially for me. So when I forget to clock out, the app isn't
going to ask "how many hours did you work yesterday" like that's a fair
question. Anchored, multiple-choice questions instead, and that time gets
marked as estimated, not treated as precise.

The other big piece today was figuring out how this plugs into OpenClaw.
I've already got it running locally with Grok 4.5 as default and a few
Ollama models as fallback, and I want this app to just use what I've
already configured instead of managing its own API keys. Turns out the
CLI has exactly what's needed for that. I also found I've already got a
full local TTS setup sitting in my AI-Setup folder from an earlier
project — Chatterbox-Turbo and Qwen3-TTS, both tested and working. So the
audio cues don't need any new setup.

Two real decisions today instead of letting Claude assume: Tauri over
Electron for the shell (lighter on the machine, I already have the Rust
toolchain installed), and timers should support more than one task
running at once, since I context-switch during a day and don't want the
app pretending I don't.

What actually got built: Tauri + React + TypeScript, Tailwind, Vitest and
Testing Library, ESLint and Prettier. Nothing exciting to look at, just a
window that says "Mycelia Time" and confirms the scaffold runs. Ran the
type checker, linter, test suite, and both builds before calling it done,
and read the actual output instead of trusting a green checkmark.

Repo is public now at github.com/TheSeeker713/mycelia-work, on main.

## 12:40 — Phase 1 (data layer, as originally numbered)

Second phase, the data layer. Nobody sees this part but everything else
depends on it.

Went with SQLite through Tauri's sql plugin, one migration creating seven
tables: tasks, task sessions, session events, notes, todos, journals, and
a resource events table for the watchdog I'm planning later. The task
session table has an `is_estimated` flag from day one — when I forget to
clock out and the app reconstructs what happened, that time gets marked
estimated, not treated the same as time I tracked live. Didn't want to
bolt that on after the fact.

The harder problem was testing. The real app talks to SQLite through
Tauri's plugin, which only works inside the running app, not a normal
test runner. Didn't want to test a fake version of the database logic
and hope it matches later. So there's one interface both the real plugin
and a plain Node SQLite connection can satisfy, and the tests run the
literal same repository code against Node's built-in SQLite, using the
exact same migration file the real app uses.

Nineteen tests, covering the stuff that matters: can't clock into a task
twice at once, can't pause a session that's already stopped, two
different tasks can run independent timers without stepping on each
other (matters since I decided on multiple concurrent timers).

The first test run actually failed, three of them — not because the
repository logic was wrong, because I'd written inconsistent test data.
One event used a hardcoded past timestamp, the event right before it
used the real current time, so of course "now" came out later than my
fake past timestamp and broke the expected order. Fixed the test data,
all nineteen passed after that.

## 12:44 — Phase 2 (task dashboard, as originally numbered)

Third phase, and the first one that actually looks like something. Task
list on the left, a workspace panel on the right that focuses on
whatever task gets clicked. No timer yet, that's next, but the shape of
the app is there.

Kept the add-a-task box as close to a single text field as I could get
away with — type what you're working on, hit enter, it's saved. Tag and
a billable checkbox sit underneath, small, since most of the time I won't
touch them.

Found a real bug writing the tests. The quick-add form has two text
inputs, title and tag, plus a checkbox. Turns out a browser only
auto-submits a form on Enter if there's exactly one text input, or an
explicit submit button. Two text inputs and no button means Enter does
nothing, silently. Wouldn't have caught that just by looking at the
code — the form looked completely normal. The test typed a title,
pressed enter, and the task never showed up. Added a small Add button,
fixed it.

Twenty-four tests passing across the project now.

## 14:57 — Design first, then a full rebuild

Told Claude to stop and design the app before touching UI code again. I
wanted to see the visual scope before making any more decisions.

Made a few calls in that conversation. No dark theme, ever, for me —
though thinking about it more, this should ship as a real setting for
other users, dark mode included, not something I ban outright just
because I hate it personally. The app should look and behave like a tiny
pocket book — small, compact, things pulled out of it when needed, full
screen "zen mode" for writing, easy to back out of, living in the system
tray as a background process, popping out an alert with a voice cue when
something needs my attention.

Then caught the devlogs themselves doing the exact thing I don't want —
four separate files for one day, and writing that reads like AI wrote
it. Specific phrases like "I want to be upfront," "I don't want to
overstep" — fine on their own, but overused and placed where a person
would just start talking instead. Had Claude research the actual
psychology behind why AI writing reads that way and what real personal
writing looks like instead — Pennebaker's expressive writing research,
blogging voice research, the pratfall effect, all of it. That's saved
now as its own reference doc so it isn't just a one-off correction.

Decided design moves to Phase 1, right after scaffold. And instead of
patching the existing work forward, we're rebuilding the whole thing
from scratch starting at Phase 0 — the data layer included, even though
it doesn't depend on the visual design at all. Git history stays exactly
as it is though, nothing gets rewritten or force-pushed away. New
commits on top, old ones stay as the honest record.

Also tightened the actual process: every step now gets its own test run,
a cross-check that nothing was hallucinated as passing, a full audit,
a retest, then commit, push, and a devlog entry — not just at the end of
a phase, at the end of every step. Only the end of a phase gets the full
stop and wait for me.

A few more real product decisions came out of that conversation too:
idle popups auto-dismiss after 30 seconds instead of blocking, assuming
I'm just busy. A session left running 8+ hours becomes a real
conversation with the AI agent instead of a static form, built around
ADHD and autism-friendly question design, one question at a time,
nothing open-ended. And there's a real answer to whether work done
outside the app — coding, editing video, whatever — can still count:
yes, because idle detection is system-wide, not scoped to this app's own
window. Good thing that got asked, because the idle-detection code
drafted earlier only listened inside the app's own window, which would
have been wrong.

Process fixes are going in now: CLAUDE.md, AGENTS.md, and
INSTRUCTIONS.md, the voice-notes reference doc, the check-in
conversation guide, and this consolidated devlog. Then the actual
rebuild starts at Phase 0.

## 15:09 — Phase 0, step 0.1: scaffold rebuilt

Cleared out the old src and src-tauri content and re-ran the Tauri
scaffold command fresh, keeping CLAUDE.md, AGENTS.md, INSTRUCTIONS.md,
and docs in place. Hit a snag doing it: the scaffold tool's --force flag
doesn't just overwrite its own template files, it wipes the whole target
directory, including things it has no idea about. Took CLAUDE.md,
AGENTS.md, INSTRUCTIONS.md, and the entire docs folder with it, gone from
disk in one command. Caught it immediately because git status showed
everything as deleted instead of just the files I meant to touch. All of
it was already committed, so `git checkout HEAD -- CLAUDE.md AGENTS.md
INSTRUCTIONS.md docs/` brought it straight back. No real damage, but a
good reminder to check status after any command that touches a whole
directory, not just the files I think it's going to touch.

Default app shell is light now, `bg-white`, not the dark neutral-950 from
before — small thing, but it's the first real piece of the design
correction actually landing in code instead of just in the plan.

Ran typecheck, lint, the test suite twice back to back as independent
confirmation (1 test file, 1 test, passing both times, which is exactly
right for a bare scaffold with the old Phase 2/3 code correctly removed),

Read all of it. Audited the diff before committing — deletions were

Phase 0 is one step for me. Stopping here to report before going further.

## 17:13 — Phase 1: the design mockup, three rounds of it

Gave the go-ahead on Phase 0 after watching the window actually open on
my own screen, so Phase 1 started, the design mockup itself.

First pass came back and something was visibly broken, screens bleeding
into each other, an idle toast and a tray bar both sitting on top of the
main view at once. Real CSS bug, not my imagination: two scene-modifier
classes had the same specificity as the rule that's supposed to hide
inactive screens, and being declared later in the stylesheet they won
regardless of which screen was actually selected. Fixed, verified by
actually clicking through every screen this time instead of trusting the
first screenshot.

Sent it over, and the feedback back was good and specific: fix the
padding, let the card scroll instead of clipping content, and where's
the button to actually write a task down. That last one mattered, since
this whole app exists because writing a task down should be
frictionless. Added a real add-task input reachable from one click no
matter where you are in the app, made Tasks/Notes/Todos all pull-tabs on
the same view instead of separate screens with no visible door into
them, and built out the auto-timestamp notes idea properly, hit enter on
a new line and the time fills itself in, autosaves the whole time,
clears the box when you leave and archives what you wrote into a
library you can actually browse. Added a daily and weekly recap card
too, plain language, not a chat, just what actually got done and what's
still sitting open.

Then the part I want to write down honestly instead of glossing over.
I said the dark mode contrast was fixed. It wasn't. I'd looked at a
screenshot, seen the switches looked better, and called it done without
actually reading whether the text next to them was legible. It wasn't,
same near-black text on a near-black background, exactly the bug I'd
supposedly already fixed. Got called on it directly, in about as many
words as you'd expect, and it was fair. Turned out to be a real CSS
lesson underneath: color inherits as an already-resolved value in
CSS, not as a live reference back to the variable, so anything that
didn't explicitly write its own color statement was quietly inheriting
the light theme's black text regardless of what the dark theme
variables said. This time I didn't just look at it, I pulled the actual
computed color values through the console, on multiple elements, across
multiple screens, both before and after the fix, and only called it
fixed once the numbers actually matched the dark palette. That's the
difference between checking and hoping, and I should have done the
first one from the start.

Same round, added books to the notes library, real ones, title and
subject and author, notes filed inside them, an AI-edit-with-a-prompt
option per note. And gave the forgot-to-clock-out check-in a way out
when the tappable answers don't fit, a genuinely messy day, two jobs and
travel and a party and one more small task before bed. Free text option
now opens a real back and forth with the agent instead of forcing one of
three canned answers, and it resolves into several separate estimated
blocks instead of pretending a chaotic day was one clean session.

Watched it live this time and it checked out. Saving the approved
mockup into docs/design/ now instead of leaving it only sitting behind
an external artifact link, so Phase 3 onward has something real and
version-controlled to build against.
