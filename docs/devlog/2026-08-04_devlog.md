## 00:48 — Two more bugs found live, both fixed: stuck journals, slow generation

Jeremy came back with two real issues from actually using the app, not
a formal test pass this time - screenshots showed session journals
sitting on "Generating…" that were clearly done being generated, just
never told the UI. Re-read `runJournalGeneration` to make sure I wasn't
about to "fix" something that was already correct - it was: every path
through it already resolves to ok or failed, confirmed by tracing the
try/catch myself. The actual gap was orphaned rows from processes that
got interrupted before that function ever got to run - a dev reload
mid-generation, or the app-freeze bug from earlier tonight, both of
which abandon the in-flight promise with nothing left to ever call
markResult() on it.

Fixed with a sweep: any journal still `pending` past 3 minutes (real
calls finish in well under a minute) gets marked `failed` with an
actual reason, the moment Library loads. Reused the existing
Failed/Retry UI instead of inventing a third "archived because it
broke" state - simpler, and it already does exactly what was needed.
Also started capturing the real caught error message on genuine live
failures now, not just a bare "failed" status with nothing to go on.

Second ask: make generation faster. Found the real cost by tracing
`run_openclaw_agent` end to end - it wasn't the model call itself, it
was waking the Gateway and immediately putting it back to sleep on
*every single* generation. A burst of clock-outs (exactly what tonight
looked like) meant paying the ~4-9s daemon-start cost over and over,
because the previous call had just shut it back down seconds earlier.
Dropped the release step from the single-shot path - the architecture
doc already justified this: an idle Gateway costs next to nothing
sitting warm, so there's no real reason to keep tearing it down between
calls that are seconds apart.

214/214 frontend tests (6 new), cargo check, cargo test (4/4), all
clean and independently re-run.

## 01:10 — Hidden Rewards/18+ unlock, exactly to spec

Jeremy brought up gamification tonight - XP, levels, milestones,
stickers - and said up front it needs real back-and-forth design before
I build any of it. Fair, and I'm holding off on that part. But he also
had one very specific, fully-specified piece ready to go: a hidden
unlock sequence gating an 18+ rewards toggle, described down to the
exact click count and the exact password.

I pushed back once on the security model before building it - this
repo is public, so "only I will have access" isn't literally true once
the sequence and a password check ship in source anyone can read. His
answer: "dont care. do it anyways" - and a detail that actually changes
the real risk picture: the assets themselves stay local, never
committed. That's the part that matters. Gitignore alone wouldn't have
been enough, though - it stops `git add`, not Vite bundling something
under `src/` into `dist/`. So instead of a gitignored folder inside the
project, the assets live in Tauri's app-data directory, genuinely
outside the repo and the build pipeline. Even someone who reads the
whole diff and finds the sequence unlocks an empty folder unless they
also have filesystem access to this machine.

Built exactly what was specced: Help > "this should not be here" (only
exists in full-screen mode, so the "full screen it first" requirement
came for free) opens a truly blank panel - three clicks, type "111",
Enter, nothing visible happening at any point, any wrong step resets
silently. Land it right and a password prompt appears; the password
itself is checked against a SHA-256 hash in Rust, not sitting in this
diff as plain text. A correct unlock persists and the Help entry
disappears for good - nothing left to find once it's found. Settings
then gets a real Rewards section with the 18+ toggle, off by default.

Caught two things worth catching. First, on myself: one of my own
first-draft tests asserted a premature keystroke should permanently
block a later correct attempt - it doesn't, and shouldn't; a stray "1"
before any clicks just resets cleanly, and the user can still complete
a valid sequence right after. Wrote the test to check what the
component should actually do, not what I'd assumed. Second, a real
robustness gap: the password check called out to Rust with no
try/catch, so an unreachable backend would throw instead of just
reading as "wrong password" - fixed to fail closed, matching how every
other backend call in this app already behaves.

## 02:23 — Phase 8.1: zen mode, the actual full-screen writing view

Jeremy confirmed everything from tonight's test round works and gave
the go-ahead to start Phase 8 - the zen mode note editor and AI
ghost-text that got assigned a phase number after he asked where it
went. Splitting it in two: this step is the writing surface itself,
no AI yet.

The real design question here wasn't the textarea - it was making zen
mode use the *same* full-screen mechanism as the rest of the app, not
a fake one. Notes' "expand" button can get clicked from either pocket
mode or from inside the app's own full-screen view, and either way it
needs to genuinely resize the OS window, then put things back exactly
how they were on exit - full screen if that's where Jeremy already
was, pocket-sized if it wasn't. That meant lifting the orchestration
up to Dashboard, which already owns the window controls, rather than
letting Notes reach for a second independent copy of window state that
wouldn't stay in sync with the one gating pocket-vs-fullscreen
rendering.

Caught one real conflict while wiring it in: the app already had a
window-level Escape handler that exits full screen unconditionally.
Zen mode needed its own Escape behavior (exit zen mode, then restore
whichever mode was active before), and the two would have fired on the
same keypress and stepped on each other - fixed by having the generic
handler skip itself entirely while zen mode is open.

The note draft itself moved from local component state into
notesStore, so the compact Notes panel and the full-screen editor
share the literal same text - write half a note, expand to zen mode,
the rest is right there; exit zen mode, the compact view has it too.
Self-voicing narrates entering and exiting like every other transition
in this app, and the same mic dictation button carries in unchanged,
per Phase 7's "every text input" rule.

245 frontend tests (9 new - two Dashboard integration tests covering
both exit paths, two in NotesCompartment for the new button, five
direct on ZenModeEditor), typecheck, lint, build all clean. Ghost-text
suggestions are the next step - this one's just the room to write in.

## 02:28 — Phase 8.2: ghost-text, closing out Phase 8

The AI half. Had to actually decide the model question the plan left
open - checked what's already pulled locally (`ollama list`) instead
of guessing, and picked dolphin-phi, the smallest one on this machine
at 1.6GB, over the 8-9B models already configured as OpenClaw's own
fallbacks. This isn't routed through OpenClaw's subprocess wrapper at
all - it's a direct call to Ollama's own local HTTP API. Ghost text
fires on every pause in typing; paying subprocess/Gateway overhead on
that cadence would have defeated "needs to feel instant" before it
even started.

Scoped the suggestion trigger to when the cursor sits at the very end
of the draft. A textarea has no built-in way to anchor an overlay
element at an arbitrary cursor position without a full caret-tracking
implementation, and zen mode's whole use case is writing forward, not
editing mid-document - so "end of text only" gets the real behavior
without the complexity a general solution would need. The ghost text
itself renders through the classic invisible-mirror-div trick: a div
behind the real textarea holds the same text in transparent ink plus
the suggestion in visible gray, sized and padded identically so the
suggestion lines up exactly where the real text stops, then peeks out
from behind since the textarea has nothing painted past its own value.

Tab accepts, any other key dismisses, per spec exactly. Added a
Settings toggle ("AI writing suggestions," on by default like the
other assistive features) since this is a background model call firing
on a timer while Jeremy's typing, same category as self-voicing and
STT as far as "give people a real off switch" goes.

256 frontend tests (11 new: fail-soft coverage on the Ollama client
itself, suggest/accept/dismiss/toggle-off behavior on the editor, the
new settings toggle both in the store and the UI), typecheck, lint,
build all clean. That's Phase 8 done - zen mode and its AI writing
assist are both real now, not a paragraph in the plan file anymore.
