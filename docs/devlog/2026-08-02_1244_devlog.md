# Devlog — Phase 2: Task Management & Workspace Dashboard

**2026-08-02, 12:44**
**Author: Jeremy Robards, CTO & CAIO, Mycelia Interactive LLC**

Third phase, and this is the first one that actually looks like something when you open it. Task list on the left, a workspace panel on the right that focuses on whatever task you click. Still no timer yet, that's next phase, but the shape of the app is there now.

I kept the add-a-task box as close to a single text field as I could get away with. Type what you're working on, hit enter, it's saved. Tag and a billable checkbox sit right underneath it, small and out of the way, since most of the time I won't touch them and I don't want them competing for attention with the one field that actually matters every single time. That's the Zeigarnik thing again, if adding a task takes more than a second of thought I'll stop doing it within a week.

For state I used Zustand, but built it as a factory instead of one global store. Sounds like a small detail but it means the tests can spin up a completely fresh, isolated store backed by the same in memory SQLite setup from phase one, instead of sharing state across tests or mocking anything. The real app just creates one store instance at startup pointed at the real database. Same code, different wiring.

Found a real bug while writing the tests today, which is exactly why I insisted on this phase by phase, test after every step approach. My quick add form has two text inputs, the title and the tag field, plus a checkbox. Turns out the browser only auto submits a form on Enter if there's exactly one text input, or if there's an explicit submit button. Two text inputs and no button means Enter does nothing, silently. I would not have caught that just by eyeballing the code, the form looked completely normal. The test typed a title, pressed enter, and the task just never showed up in the list. Added a small Add button, which fixed the actual bug and also made the form more honest about what it does, since relying purely on invisible enter key behavior isn't great UX anyway.

Twenty four tests passing across the whole project now, typecheck clean, lint clean, both builds compiling. Read every bit of that output myself before calling it done, same as yesterday.

Multi timer core is next. That's where the app starts doing the actual job it's for, clocking in, breaks, clocking out, and the beginning of the idle detection and forgot to clock out recovery flow I care about a lot.

— Jeremy
